# Аудит кода перед редизайном

Дата: 2026-09-21. Ветка: `feature/redesign`. Объём: ~7 600 строк Swift.

Область аудита: **модели, движок, хранилища, настройки проекта** — то, что переживёт
редизайн. Слой представления (`iPhone_Views`, `iPad_Views`, `Common_Views`) намеренно
проверен только поверхностно: по спеке он переписывается с нуля, глубокий разбор кода,
который будет удалён, — потраченное время.

Оценка серьёзности: **A** — надо чинить, **B** — стоит починить при переписывании,
**C** — косметика / долг.

---

## 1. Архитектура

### A1. Правила игры реализованы трижды

| Реализация | Файл | Кто использует |
| --- | --- | --- |
| `GameEngine.checkShipOnFire` | `Models/GameEngine.swift` | игра против компьютера |
| `HotSeatGame.fire` | `Models/HotSeatGame.swift:150` | вдвоём на устройстве |
| `NetworkGame.resolveIncomingShot` | `Models/NetworkGame.swift:176` | сетевые режимы |

Каждая по-своему определяет попадание, потопление, конец партии. Баг, найденный в одной,
надо чинить в трёх местах. «Игра на бумаге» станет **четвёртой** копией.

**Что делать:** вынести чистое ядро правил (`BoardState` + `Rules`) без зависимостей от
`AppState`, звука и хранилищ. Все четыре режима — тонкие адаптеры над ним. Это
предварительное условие для новых режимов, а не украшение.

### A2. Сторона игрока определяется сравнением строк

`target.name == "Player"` / `== "Enemy"` — в `GameEngine` (6 мест), `PlayerData`
(`shipsRandomArrangement`). Строка `name` при этом же используется как отображаемое имя.

Последствия: нельзя переименовать сторону, нельзя локализовать имя, в режимах «человек
против человека» понятие «Player/Enemy» вообще не отображается на роли. В новом дизайне
роль («ты» тёплый / «соперник» холодный) — центральное понятие (правило 4 спеки).

**Что делать:** `enum Side { case you, foe }` как идентичность, `displayName` отдельно.

### B3. Координаты — кортежи `(Int, Int)`

`Ship.coordinates: [(Int, Int)]`, `appState.potentialCellsForFinishingDamagedShip`,
возвраты `definePriorityTargetCells`. Из-за этого `Ship` нужен рукописный `Codable`,
нет `Equatable`/`Hashable`, а `.0`/`.1` регулярно путаются (row/column).

`Coordinate` (Codable, Hashable, Sendable) уже написан в Phase 0 и используется только
в сериализации. Миграция откладывалась — сейчас последний удобный момент, до того как
новые экраны начнут читать кортежи.

### B4. `definePriorityTargetCells` читает не ту доску

`GameEngine.swift:107` принимает `row`/`column`, но внутри всегда обращается к
`player.cells`, игнорируя, по какой доске был выстрел. Сейчас работает, потому что
вызывается только из ветки `target.name == "Player"`. Мина на будущее.

### B5. `GameEngine` знает слишком много

Один метод `checkShipIsTotallyDestroyed` одновременно: меняет клетки, останавливает
музыку, стирает сохранение (`GameStore.clear`), пишет статистику (`ProgressStore`),
запускает `Task` со `sleep(1)` для показа алерта. Из-за этого ядро нельзя протестировать
без UserDefaults и файловой системы.

## 2. Корректность

### A6. Уровни «Легко / Средне / Сложно» ведут себя одинаково

`ComputerOpponent.meetConditionsToDefineCellForFire` (`:279`) — три ветки из четырёх
возвращают ровно `cells[...].isAvailable`. Комментарии «more logic» / «more complex logic
here to come» остались с Phase 0.

Единственная реальная разница: в `GameEngine.swift:80` на `.easy` компьютер не исключает
кольцо вокруг потопленного корабля. То есть **medium и hard неотличимы**, а игрок за них
платит вниманием в настройках. В новом дизайне статистика ведётся по четырём уровням —
расхождение станет заметным.

### A7. Сетевые победы засчитываются как победы над «Экспертом»

`NetworkGame.swift:248`: `ProgressStore.shared.recordWin(at: .expert)` и `:154`
`addPoints(expert.pointsValue)`. Победа над живым человеком по сети попадает в графу
«против компьютера · Эксперт». Новый дизайн показывает эти графы раздельно (раздел 4.9
спеки), так что расхождение вылезет наружу.

### A8. `fireStrokeArray` растёт как треугольник

`AppState.resetData` (`:120-131`) и `PlayerData.init` (`:213-222`): `boolArray` объявлен
**до** внешнего цикла и `append(false)` идёт во внутреннем, без сброса. В итоге строка 0
содержит 10 элементов, строка 1 — 20, … строка 9 — 100. Вместо 100 значений хранится 550
на каждую сторону.

Падения нет (используются только первые 10 индексов), но это явная ошибка, она же
дублируется в двух местах.

### B9. Громкость выставляется после старта воспроизведения

`AppState.playSound` (`:96`): `soundPlayer?.play()` идёт **до** `soundPlayer?.volume = level`.
Первые миллисекунды звук играет на громкости по умолчанию.

### B10. Каждый выстрел создаёт новый `AVAudioPlayer`

`playSound` каждый раз декодирует файл и присваивает единственному статическому
`soundPlayer` — предыдущий звук обрывается на середине. При частых выстрелах это заметно
и на слух, и по main-thread аллокациям.

**Что делать:** сервис звука с предзагруженными плеерами по событию, пул на несколько
одновременных.

### B11. Звук попадания собирается двумя путями

`GameEngine` копит имя файла в свойстве `sound` (мутабельное состояние между строками
одного метода) и играет его сам; параллельно `GameLogicViewModel.chooseSound` играет
звук за игрока по статусу клетки. Для стороны противника `sound` остаётся `""` и
`playSound("")` уходит в `guard`. Работает, но понять это можно только чтением обоих
файлов.

### B12. `schemaVersion` пишется, но не проверяется

`GameSnapshot.schemaVersion = 1` (`:53`) — при загрузке (`GameStore.load`) не читается.
Смена формата приведёт либо к молчаливому `nil`, либо к неверным данным. Нужен явный
разбор версии (сейчас достаточно «версия != текущей → считать сохранение отсутствующим»).

### B13. Отложенный сброс подсветки не отменяется

`GameLogicViewModel.performShot` (`:68-71`) — `Task` со `sleep(0.3)` пишет
`player.fireStrokeArray[...] = false`. Задача не хранится и не отменяется; если за эти
0,3 с началась новая партия, запись уйдёт в уже пересозданный массив.

### C14. `difficulty` хранится как «магический» Int

`AppState.difficultyLevel` (`:139`): `0 → hard, 1 → medium, 2 → easy, 3 → expert`.
Порядок неочевиден, значение пишется в `UserDefaults` и в `GameSnapshot` сырым числом.
Правильнее хранить `DifficultyLevel.rawValue` (строку, `Codable` уже есть).

### C15. `defineSafeAreaNearShip` против `markSafeAreaAsMissed`

Две функции делают одно (кольцо вокруг корабля), но первая — 30 строк ручных смещений с
предположениями о порядке координат, вторая — 12 строк через `min/max` + клампинг.
Первую надо переписать во втором стиле.

## 3. Производительность

### B16. Поиск клетки для выстрела — «бросай кубик, пока не попадёшь»

`ComputerOpponent.findAvailableCellsForFire` (`:258`): `repeat { random(1...10), random(1...10) }
while !доступна`. К концу партии свободных клеток единицы, ожидаемое число итераций
растёт до сотен. Зависания нет, но это лишняя работа на каждый ход.

**Что делать:** собрать список доступных клеток и взять `randomElement()` — O(100) один раз.

### B17. Сохранение на главном потоке после каждого выстрела

`GameLogicViewModel.autosave` → `GameStore.save` — синхронные `JSONEncoder` + запись файла
на `@MainActor`. Файл небольшой, но на каждый выстрел это лишний I/O в кадре.
Debounce или запись в фоне.

### C18. Рекурсия вместо цикла

`performShot` вызывает `await performShot()` при попадании. Глубина ограничена 20
попаданиями, так что практической проблемы нет, но цикл `while` читается лучше и не
растит стек.

## 4. Готовность к Swift 6

Текущее состояние таргета `SeaBattle`:

| Настройка | Сейчас | Цель |
| --- | --- | --- |
| `SWIFT_VERSION` | 5.0 | 6.0 |
| `SWIFT_STRICT_CONCURRENCY` | minimal | complete |
| `SWIFT_APPROACHABLE_CONCURRENCY` | NO | YES |
| `SWIFT_DEFAULT_ACTOR_ISOLATION` | nonisolated | MainActor |
| `SWIFT_UPCOMING_FEATURE_EXISTENTIAL_ANY` | No | YES |
| `IPHONEOS_DEPLOYMENT_TARGET` | 18.0 | см. открытый вопрос |

Что сломается при переключении на `complete`:

1. **`AppState.musicPlayer` / `soundPlayer` / `shipIsPlaced`** (`AppState.swift:68-70`) —
   мутабельные глобальные `static var`, это ошибка в Swift 6. Уходят в изолированный
   сервис звука.
2. **`AppState` не изолирован**, но трогает `AVAudioSession`, `UIScreen`, `UIDevice`.
   Должен стать `@MainActor` (или весь модуль — через `SWIFT_DEFAULT_ACTOR_ISOLATION`).
3. **`AppState.isPad` / `deviceHasWideNotch`** — обращение к `UIDevice.current` /
   `UIScreen.main` вне main actor. Плюс `UIScreen.main` устарел в многооконной среде;
   в новом дизайне размеры и так берутся из size class / `GeometryReader`.
4. **Неявно развёрнутые опционалы** `appState: AppState!`, `player: PlayerData!`,
   `opponent: Opponent!` в `GameEngine` и `GameLogicViewModel` — не ошибка Swift 6, но
   `configure()`-после-`init()` плохо дружит с новым деревом представлений.
   Ядро правил должно создаваться уже полностью инициализированным.

Рекомендуемый порядок: `complete` → починить → `SWIFT_VERSION = 6.0`. Делать это **до**
написания новых экранов, иначе те же ошибки придётся чинить и в новом коде.

## 5. Слой представления (поверхностно)

Хорошее: нет `NavigationView`, нет `AnyView`, нет `DispatchQueue`, нет `ObservableObject`
/ `@Published` (весь проект уже на `@Observable`), нет проверок `colorScheme`.

- **C19. Дублирование iPad V/H.** 12 файлов парами (`iPadMainViewV/H`, `iPadMenuViewV/H`,
  `iPadAboutViewV/H`, `iPadGameScoreViewV/H`, `iPadBattleViewV/H`,
  `iPadShipArrangementMenuViewV/H`) — примерно 1 400 строк почти одинакового кода.
  По новой спеке структура одна на все режимы и ориентации, различаются значения —
  дублирование уходит целиком.
- **C20. Устаревшая форма `onChange`.** Однопараметрические замыкания в
  `YourTurnButtonView.swift:42`, `SettingsView.swift:33,72,85,94` — soft-deprecated с
  iOS 17.
- **C21. Опечатка в имени файла** `iPadMenuBattonsViewH.swift` (Battons → Buttons).
- **C22. 5 вызовов `print`** в обработке ошибок вместо `Logger` (`os.Logger`).

Сгруппировано в задачи в `docs/REDESIGN_PLAN.md`. Коротко:

1. **До дизайна** (шаг R0): Swift 6 + чистое ядро правил + `Side`/`Coordinate`.

3. **A6** (одинаковые уровни сложности) и **A7** (сетевые победы в графе «Эксперт») —
   продуктовые решения, вынесены в вопросы, а не в код.
